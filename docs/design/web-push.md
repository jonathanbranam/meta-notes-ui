# Web Push to the phone

Status: design for review (ticket `web-push-to-the-phone-for-timed-tasks-and-the-time-block-des-6u38`).
No code until the human approves. Written for a 10-minute read.

## What this is

Today the app alerts you only while a tab is open: the browser holds one timer
per alert (`client/src/TodayView.tsx`, `client/src/today.ts`). With the phone
locked or the app closed, nothing fires. This design adds real push: the server
on the NUC sends a message through Apple's push service at the right time, and
the phone shows it even when the app is closed.

Scope: the alerts the app already builds (timed tasks due today, the next
planned Time Block row). Nothing new to alert on.

No Apple Developer account, no signing, no certificate. Standard Web Push
needs only the server's own key pair (VAPID), a Home Screen PWA on iOS 16.4 or
later, and HTTPS. All of those are in place or generated by the server.

## The short version

- It is the existing Node server (`meta-notes-ui.service`, port 7480). One new
  module; no new process, no new unit.
- The server makes a plan of today's alerts from the notes, sets **one timer**
  for the earliest unsent alert, and re-plans when a note changes. No polling.
- At fire time it sends one Web Push to each subscribed device. The phone's
  service worker shows it.
- The phone subscribes once from the app (the "Enable alerts" button).
- Alert ids are shared with the in-app alerts, so one alert is one
  notification, not two.

## 1. What runs on the server

The existing Node server, started as today by the systemd user unit
(`deploy/meta-notes-ui.service`, `deploy/nuc.md`). It must stay running for
pushes to go out, and it already does: `loginctl enable-linger` keeps the user
unit alive without a login, `Restart=on-failure` brings it back after a crash,
and `WantedBy=default.target` starts it at boot.

Restarts are normal here: the update path unit rebuilds and restarts the
server whenever `main` moves. So the scheduler keeps nothing only in memory
that it cannot rebuild (see 2). On every start it reads the notes, rebuilds
the plan, and reads what was already sent from disk.

Nothing changes in the unit file. The server gains one optional flag,
`--push-contact <mailto:...|https://...>` (the VAPID "subject", see 3); without
it the push module is off, the way the Message button is off without its flags.
Push stays optional.

## 2. Scheduling: how it knows, how it wakes

### What gets scheduled

The same alerts the client builds now: a timed task due today (a time of day after the alarm-clock mark), and
each planned Time Block row whose plan differs from the row before. The logic
is `buildAlerts` and `parseTimeBlock` in `client/src/today.ts`. The build moves
that code (and its tests) to `shared/` so server and client use one copy; the
ids stay exactly `task:<file>:<line>:<time>` and `row:<HH:MM>`.

The server gets its inputs the way `GET /api/today` does (`server/today.ts`):
`meta-notes tasks --overdue --due --json` and the daily note named by
`meta-notes note daily --render` (which never creates the note). Reading goes
through the CLI and the files; the server writes no note (`writes-through-the-cli`).

### How it wakes: one timer, not a poll

After planning, the server finds the earliest alert that is in the future and
not yet sent, and arms a single `setTimeout` for it (clamped, since Node caps a
timer near 24.8 days; in practice the longest wait is until midnight). When it
fires, the server sends, marks it sent, and arms the next. There is no
interval that scans files (`light-on-resources`).

A second timer re-plans just after local midnight, so tomorrow's alerts exist.

### How it notices edits

It re-plans on the watcher events it already has (`server/watcher.ts`, the
`subscribe` hook in `server/start.ts`): when a change touches a `.md` file,
after a short debounce (about 2 seconds, so a `git pull` or an agent writing
ten notes runs the CLI once), it re-reads the inputs and re-arms the timer.
Cost: one `meta-notes tasks` run per burst of edits, the same cost the open
page already pays on each change. If no device is subscribed the server skips
all of this.

Consequences of the shared ids:

- A task whose time you change gets a new id, so it alerts at the new time. If
  the old time was already sent you may get one extra alert. Acceptable.
- A task checked off or moved to another day drops out of the plan; its pending
  timer goes away at the next re-plan.
- An edit made within the debounce of an alert's time can race it. At worst the
  alert goes out on the old text. Not worth guarding.

### What is remembered (and where)

A small `sent.json` (alert id plus date) so a restart or a re-plan never sends
the same alert twice. It sits beside the keys, see 3. Entries older than a day
are dropped on load.

### Missed sends

If the server was down at an alert's time (a rebuild, a crash, a reboot), then
on start:

- An unsent alert that is **at most 10 minutes late** is sent now, with its
  normal text.
- Anything later is skipped and marked sent. A 9:00 "start work" at 11:30 is
  noise, and a flood of old alerts after a long outage is worse than silence.

Ten minutes is a constant, not a setting (`yagni`).

The NUC does not suspend, so timer drift from sleep is not a concern. If that
changes, the fix is to re-plan on resume, not to poll.

### Time zone

`buildAlerts` uses the process's local time, as the client does. The NUC's zone
is US Eastern (`date` prints EDT), which matches the human. The build should
state in `deploy/nuc.md` that the unit relies on the host zone.

## 3. Web Push mechanics

### Keys (VAPID)

A VAPID key pair is a P-256 key the server uses to prove to Apple's service that
the pushes come from the same server the phone subscribed to. It is not an
Apple credential.

- **Generated** by the server on first start with push enabled (Node's
  `crypto`), never by hand.
- **Stored** in `<notes>/.meta-notes-cache/ui/push/vapid.json`, mode 0600, next
  to the token and login files. That directory is already git-ignored in the
  notes repo, so keys never reach git (the same reason the token is there).
- The **public** key is served to the page at `GET /api/push/key`; the private
  key never leaves the file.
- Losing the file invalidates every subscription (the phone must re-enable
  alerts). Not a disaster; see risks.

The VAPID "subject" (`--push-contact`) must be a `mailto:` or `https:` URL.
Apple rejects pushes without a valid one. The human supplies it in the unit's
`ExecStart`; the design does not guess an address.

### The phone's subscription

1. In the installed app, the existing "Enable alerts" button
   (`TodayView.tsx`) already asks for notification permission. It also calls
   `registration.pushManager.subscribe({ userVisibleOnly: true,
   applicationServerKey })` with the key from `/api/push/key`. iOS requires
   this to come from a tap, and requires the app to be on the Home Screen.
2. The browser returns a subscription: an Apple URL (the "endpoint") plus two
   keys. The page `POST`s it to `/api/push/subscribe` (cookie or login needed,
   as for every request, `access` rule).
3. The server stores it in `.meta-notes-cache/ui/push/subscriptions.json`,
   keyed by endpoint, with a created date and a short device label from the
   user agent. Several devices work (phone plus a desktop browser).

**Expiry and renewal.** A subscription ends when the browser drops it, the app
is removed, or Apple answers 404 or 410 to a send. The server deletes it on
such an answer. On the client, two things heal it: the service worker's
`pushsubscriptionchange` event re-subscribes and re-posts, and the page
re-posts its current subscription on each load (an idempotent upsert), so a
server that lost its file learns it again the next time the app opens. A
transient failure (5xx, network) is retried once a minute for a few minutes,
then dropped for that alert, not that subscription.

**Turning off.** An "Alerts off" action unsubscribes in the browser and
`DELETE`s the entry. Small; part of the build.

### What goes over the wire

The server encrypts the payload to the phone's keys and `POST`s it to the
endpoint over HTTPS. Payload: `{ title, body?, tag, url }`. Size is far under
the 4 KB limit. Mechanics (VAPID JWT, aes128gcm encryption) are done by the
`web-push` npm package, a public package. It adds one dependency (and a few
small ones under it); that is called out here because the dependency tree is
meant to stay small. See rejected alternatives for hand-rolling.

### The service worker

`client/public/sw.js` gains a `push` handler:

```js
self.addEventListener("push", (e) => {
  const d = e.data ? e.data.json() : { title: "meta-notes" };
  e.waitUntil(self.registration.showNotification(d.title, { body: d.body, tag: d.tag, data: { url: d.url } }));
});
```

It always shows a notification: Safari revokes the subscription of a site that
receives pushes and shows nothing. The existing `notificationclick` handler
opens `/#!today` and gains: open `data.url` when given. It still caches
nothing.

### Outbound access

The NUC needs outbound HTTPS (443) to the push service named in each
subscription's endpoint: `web.push.apple.com` for iOS Safari and Home Screen
apps, and for other browsers Google (`fcm.googleapis.com`) or Mozilla
(`updates.push.services.mozilla.com`). No inbound port, no change to
`tailscale serve`. If the NUC sits behind a proxy or an egress allowlist, those
hosts need allowing; the build checks outbound reachability first.

### Apple account and certificate: confirmed not needed

Web Push on iOS uses the open standard with VAPID. There is no App Store
build, no APNs certificate and no Developer Program membership. The needs are
iOS 16.4+, the app added to the Home Screen, a tap to grant permission, and
HTTPS (we have it through `tailscale serve`).

## 4. Fit with the in-app alerts (ticket 35z9): no doubles

Both sides already name an alert the same way (`Alert.id`), and the client
already shows its notification with `tag: a.id`.

The rules:

1. **The server sends every alert** to every subscribed device, whether or not
   the app is open. It does not know what is open.
2. **The service worker shows each push with `tag = alert id`.** A second
   notification with the same tag replaces the first, silently, so two
   deliveries of one alert are one notification on the lock screen.
3. **A device that has a push subscription stops showing its own system
   notification** from the page (`notify()` in `TodayView.tsx` is skipped). The
   page still adds the alert to the in-app list with Dismiss and Snooze
   (`FiredAlerts`), as now. A device with no subscription (a desktop tab, or
   alerts not yet enabled) works exactly as today.
4. **The service worker does not hide a push because the app is open.** That
   would be the obvious way to avoid a double, but Safari penalises silent
   pushes (see 3).

Snooze stays local to the page and does not reschedule a push in v1 (deferred).

Open point to test on the real phone: whether iOS draws a system banner for a
push while the Home Screen app is in the foreground. If it does and that is
noisy alongside the in-app list, the fallback is for the service worker to
show then immediately `close()` the notification when a visible window exists.
That is a build-time check, not a design fork.

## 5. Room for ticket gnqx (agents sending pushes)

One small seam, no more:

```ts
// server/push.ts
sendPush(p: { title: string; body?: string; tag: string; url?: string }): Promise<{ sent: number; removed: number; failed: number }>
```

It sends to all stored subscriptions, deletes the dead ones, and is what the
scheduler calls. The payload shape is exactly what the service worker's `push`
handler reads, so a later sender needs nothing in the client.

gnqx would add its own route (and how a bridle agent reaches it) on top of
`sendPush`. This design adds no such route and does not decide how agents are
authenticated or how the Message button's bridle link is used: that is gnqx's
design (`yagni`). The `tag` field is the part to keep stable: an agent's
message can pick its own tag so repeats collapse.

### How to verify it

- Executable specs under vitest, with a fake clock (`vi.useFakeTimers()`) and
  a fake sender (no network): the plan from a fixture notes root, the timer
  fires the right alert once, an edit re-plans, a restart does not resend, a
  9-minute-late alert sends and a 30-minute-late one is skipped, a 410 answer
  removes the subscription, two deliveries of one id share a tag.
- Server tests on port 0 (never 7480); the key file is created 0600 under the
  fixture root.
- `npm run check` green.
- The real-phone test (subscribe, lock the phone, wait for a timed task) is the
  human's, after the unit rebuilds from `main`. Agents never touch the human's
  server (`human-server` rule).

## Rejected alternatives

- **A native iOS app or APNs.** Needs the Developer Program, certificates and
  App Store or TestFlight. Web Push does the job with none of it.
- **Keep client timers only.** What exists. A closed or locked phone gets
  nothing; that is the whole problem.
- **A polling loop on the server** (check every minute). Simple, but it is the
  timer-that-scans-files that `light-on-resources` forbids, and it drifts from
  the exact minute.
- **A cron or systemd timer per alert.** Needs a writer of timers outside the
  server, a second moving part to keep in sync with the notes. One in-process
  timer is simpler and restarts cleanly.
- **A separate scheduler process or unit.** Would need its own supervision and
  its own view of the notes. The server already has the watcher, the CLI
  wrapper and the subscriptions.
- **A third-party push service** (OneSignal, ntfy, Pushover). Notes content
  leaves the machine and an account is needed. Web Push sends directly, and the
  payload is encrypted end to end.
- **Hand-rolling VAPID and payload encryption with `node:crypto`.** About 150
  lines, no new dependency, but easy to get subtly wrong and untestable
  against a real service in CI. The small, widely used `web-push` package is the
  better trade.
- **Payload-less pushes** (the push only wakes the service worker, which then
  fetches what to show). Avoids encryption, but the worker must make an
  authenticated fetch and still show something before the OS gives up; more
  failure modes than an encrypted payload.
- **Hiding the push when the app is open.** Safari treats silent pushes as
  abuse and can revoke the subscription. Shared tags are the safe way.
- **Per-alert snooze via push actions.** iOS does not support notification
  action buttons for web apps in a useful way.

## Deferred (not yet, with reasons)

- **Server-side snooze.** Needs a way to answer a notification; iOS has no
  usable action buttons, so it would be a tap into the app. Wait until the
  basic flow is used.
- **Other alert kinds** (calendar agenda events, overdue reminders). The human
  asked for what the app already alerts; add when wanted.
- **Quiet hours and per-kind settings.** No need shown yet.
- **A push log or history view.** `journalctl` is enough to start.
- **The agent push route (gnqx).** Its own design and task.
- **Multi-root or multi-user keys.** One notes root, one human.

## Risks

- **iOS quirks.** Push works only for the Home Screen app, iOS 16.4+; a user
  who denies permission must fix it in Settings; iOS may delay or drop
  pushes under Low Power Mode. Mitigation: the Today view already says when
  alerts are blocked; the build adds "subscribed" state next to it.
- **Safari revoking the subscription** if it ever receives a push and shows
  nothing. Mitigation: the worker always shows (4.4).
- **Restarts around an alert's time.** The path unit restarts the server on
  every merge to `main`. Mitigation: the sent file and the 10-minute catch-up.
- **Host time zone.** If the NUC's zone changes, alerts shift. Mitigation: a
  note in `deploy/nuc.md`.
- **Lost key file** drops all subscriptions silently. Mitigation: pages re-post
  on load, and a changed key makes `subscribe` fail loudly, which the page
  turns into "re-enable alerts".
- **New dependency** (`web-push`). Mitigation: it is the only one, public, and
  named in the build handoff.
- **Outbound blocked** (egress rules). Mitigation: reachability check first.
- **Notes content in a push.** Titles like "09:30 Call the dentist" pass
  through Apple's service, encrypted to the phone, but Apple sees timing and
  size. Same trust as any push; tell the human.
