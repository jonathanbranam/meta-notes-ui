Nobody builds until the human approves; the build is a separate task filed afterwards with --from mu-6u38.

The design must answer the human's questions in plain terms:
1. What runs on the server: is it the existing Node server, and does it have to stay always on (how it's started and kept running on the NUC, and what happens after a restart or reboot)?
2. Scheduling: how the server knows when to send (timed tasks, the next Time Block row), how it wakes at the right time (timers vs a polling interval; how it notices edits to notes), and what happens with missed sends while it was down.
3. Web Push mechanics: VAPID keys (where they're generated and stored, kept out of git), the phone's subscription (how it's created from the PWA, where it's stored, what happens when it expires), the service worker's push handler, and outbound access to Apple's push service. No Apple Developer account or certificate is needed; confirm that.
4. How it fits with the in-app alerts the app already shows (ticket 35z9): no double alerts when the app is open.
5. Room for ticket gnqx (bridle agents sending pushes to the phone) later: a small send interface it can reuse. Don't design gnqx itself (YAGNI).
Also list rejected alternatives, what is deferred, and the risks.

Model: sonnet. Read the existing server and the alerts code (ticket 35z9 and its design) first. Keep it to an overview the human can read in about 10 minutes.
